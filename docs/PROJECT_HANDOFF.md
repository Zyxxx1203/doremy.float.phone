## 0. 接手时必须先读的规则

1. **唯一当前主仓库：** `Zyxxx1203/momo.float.phone`。
2. **代码变更直接进入 `main`。** 用户明确要求所有后续改动直接提交 main，不要另开分支或 PR。提交前先读 main 当前实际代码，不能根据旧聊天或提交标题猜实现。
3. **先查根因，再成组重构。** 用户反感“七补一点八改一点”的零碎补丁。涉及一个功能的布局、交互、状态和样式时，要先梳理整体结构和事件流，再一次性形成完整方案；不能在不了解上下文时继续叠加 CSS/事件补丁。
4. **保留原功能和数据。** 改 UI 不应无意改变业务逻辑、存储结构、历史记录、偏好设置或其他页面。若必须迁移数据，应兼容旧数据并提供安全回退。

6. **优先可用性，其次装饰动画。** 整个点击区域都应可点击；移动、涂鸦、播放、滚动、全屏等核心交互稳定后再做动画。
7. **目标环境：** Netlify/自托管网页、PWA、Android WebView/APK；兼顾窄屏、横屏、刘海和系统安全区。不能只在桌面浏览器上设计。
8. 用户希望的协作方式：用户集中提出需求，开发者尽量一次性完成相关实现、自检、构建和回归；除非存在必须确认的产品决策，不要频繁打断确认。

## 1. 项目定位与技术背景

这是一个以网页为主体、可经 Android 原生 Shell/WebView 打包为 APK 的 AI 角色陪伴/虚拟手机项目。既有聊天、角色设定与记忆、工具调用、生活系统、照片墙、一起看、推送、云备份等功能；Android 能力通过现有原生桥接和服务补充。不能把它当作单一展示网页，也不能为了某个页面重构破坏其他模块。

- 当前仓库：`Zyxxx1203/momo.float.phone`
- 默认工作分支：`main`
- 主要前端：Next.js / React / TypeScript；部分 Android Shell 代码为 Kotlin。
- 相关文件（路径可能随版本调整，接手时请重新核实）：
  - 一起看：`components/watch-together-app.tsx`
  - 照片墙主界面：`components/photo-wall-app.tsx`
  - 照片墙画布：`components/photo-wall/photo-wall-canvas.tsx`
  - 照片墙模板：`lib/photo-wall-templates.ts`
  - Android WebView 主 Activity：`android-shell/app/src/main/java/app/floatphone/shell/MainActivity.kt`
- 自托管部署相关历史配置：`NEXT_PUBLIC_SELF_HOSTED_MODE=true`；实际部署配置应以 main 当前文件为准。
- 云备份使用 Supabase 是用户有意保留的选择，不能擅自因成本/依赖问题迁走。

## 2. 用户的产品与协作偏好

### 2.1 通用界面原则
- 要做的是完整的页面体验与视觉语言，不是只换主题色或改几个圆角。
- 不要擅自改页面标题、文案和功能名称来假装完成视觉重构。
- 避免默认模板感、过多大圆角卡片、拥挤、元素互相遮挡、文字被截断、无效的大图标和不可点击的装饰。
- 控件的图标、文字和留白都应在整个按钮命中区域内响应；小屏下不能出现加号菜单被遮住、工具栏盖住内容、弹窗或输入框不可操作等问题。
- 保留已有功能。先确保交互可用、布局正确、滚动独立，再统一细节和动画。
- 不要在没有必要时生成参考图片；用户一般偏好直接改代码和文字沟通。

### 2.2 生活系统视觉方向（背景要求）
- 方向：法式玫瑰庄园 × 复古植物图鉴 × 奶油色高级生活方式 App。
- 主色为奶油白、米白、浅粉/雾粉、少量金色和灰绿点缀；用户明确不喜欢绿色占主导。
- 需要可感知的全页面装饰与统一设计语言，不只是主题色；但装饰不能挤占聊天内容或干扰操作。
- 场景卡可像复古明信片，行程像邀请函，地点像图鉴；必须根据实际功能结构设计，不能照搬样图。
- 聊天空间优先；字号、边距等设置要简洁、直接输入数值，不能让设置面板把内容压住。
- 生活系统聊天：动作/旁白/角色发言需要清楚区分。动作/旁白用小号、居中、斜体的叙述表现，不做成普通角色气泡；角色发言独立显示。用户曾要求默认对白字号 13、气泡内边距 3。
- 角色头像已能区分说话者，不要在气泡里重复加突兀的角色名字标签。

## 3. 一起看（Watch Together）：产品目标与当前阻塞

### 3.1 目标体验
一起看应是温暖、沉浸、完整可用的共同观影空间，不应只是普通播放器上叠几个卡片。设计与照片墙应相互独立。

预期结构：
1. 视频屏幕是页面视觉中心，能真正播放、暂停、拖动进度、切换全屏。
2. 无视频时的占位区域应轻量；用户明确要求**删除**文案为“想看的内容放上屏幕等待开始 · 选择视频或粘贴链接”的那张卡片。
3. 将原来放在下方的角色头像与电波/连接动画移到这块屏幕占位区域中，取代该卡片；要把原本堆叠在底部的卡片拆开，按实际职责重排，不是把整张卡片原样搬上去。
4. 屏幕下方显示角色最近发言，再下方是讨论输入区；互动操作与完整讨论历史清楚分区。历史列表应可独立滚动。
5. 保留已有角色、语音/主动发言、字幕/弹幕、讨论记录、时间点标记、交互按钮等功能；主动发言间隔的用户偏好要持久化，不能随意改掉。
6. 进入全屏后必须是**真正的沉浸式全屏**：视频画面不被应用顶栏、原生壳层或电波卡片遮挡；左上角不要再出现悬浮电波卡片。退出后恢复原布局与横竖屏状态。
7. 用户明确希望像 B 站一样在视频画面上发送/显示弹幕（danmaku），并防止弹幕相互遮挡：弹幕碰撞/布局判定要控制重叠度，**重叠度不得超过 50%**。需要定义可计算的重叠指标和碰撞策略；不能仅用随机位置假装解决。
8. 所有可视控件都必须有实际行为。用户报告屏幕中央有一个很大的图标但点了没有反应，应查明它的用途与事件绑定；如果没有必要就移除，不得保留无效的大图标。

### 3.2 用户当前明确报告的回归/未解决问题（最高优先级）
以下来自用户 2026-10-21 的最新反馈，必须视为**尚未解决**，不能因为此前有代码提交就认为已修复：
- 仍出现“想看的内容放上屏幕等待开始 · 选择视频或粘贴链接”卡片；用户要求移除，并把下方头像和电波放进其原位置。
- 页面需要整体重构，不能继续零散补丁。
- 网页端仍无法播放小红书分享链接。
- 屏幕中央大图标点击无响应。
- 全屏时视频画面卡在第一帧。
- 全屏左上角电波卡片遮挡屏幕；用户明确不要它。
- 全屏要真全屏并支持 B 站式弹幕。
- 弹幕重叠度不超过 50%。
- 讨论/触摸区域交互不能为了全屏而破坏普通操作。

### 3.3 小红书链接播放的技术边界
- 不要宣称“支持所有链接”。小红书分享链接常涉及跳转、页面脚本、登录态、签名参数、反爬、跨域、临时 CDN 地址或防盗链；普通网页 iframe/直接赋给 video.src 并不能保证拿到真实媒体流。
- 先沿现有解析链路定位：输入 URL 规范化 → 分享链接跳转/落地页 → 页面数据/接口提取 → 媒体 URL → 播放器 source → 浏览器/WebView 的 CORS、MIME、Range、Referer 等限制。每一阶段要显示具体失败原因，而不是统一显示“解析失败”。
- 直接媒体（MP4/HLS）与平台网页链接要分开处理；如果拿不到真实可播放媒体地址，应明确告诉用户当前环境不支持，而不是假装已解析。
- 不要重新加入已移除的公共 CORS 代理作为通用绕过方案。不要尝试绕过 DRM、登录授权或其他访问控制。
- Android 原生桥接可辅助打开外部 URL 或在合法范围内解析，但网页和 APK 的能力不同，状态与提示必须准确区分。
- 验收需要真实的小红书分享链接和目标环境测试；没有真实链接/真机测试就只能报告“尚未验证”。

### 3.4 一起看建议的重构顺序
1. 先梳理 `components/watch-together-app.tsx` 中播放器状态、解析状态、全屏状态、方向变化、角色伴随 UI、讨论列表和输入框之间的关系。
2. 查明视频第一帧冻结：核对 video 的 source 更新时机、`load()` / `play()`、异步解析竞态、`loadedmetadata` / `canplay` / `playing` / `waiting` / `error` 事件、全屏前后的 DOM/播放器重建，以及方向切换时是否错误恢复了旧时间或旧 source。不要只延迟几百毫秒掩盖根因。
3. 查明 WebView 真全屏支持。若调用 Fullscreen API，确认 Android WebChromeClient 的自定义全屏视图回调与退出回调是否实现；仅把容器设成 fixed 不是原生 WebView 的完整全屏保证。
4. 重做页面结构：屏幕/空状态、屏幕内弹幕层、屏幕下角色消息、输入区、互动区、历史区各有清晰职责；删除重复卡片和无效图标。
5. 再实现弹幕碰撞检测、移动动画、输入与历史存储，并处理窄屏/横屏/安全区。
6. 逐个测试普通网页、PWA、Android WebView/APK。检查全屏进入/退出、旋转、返回键、播放时间、播放/暂停、弹幕与输入区是否互相抢事件。

## 4. 照片墙（Photo Wall）：产品目标与当前严重回归

### 4.1 目标体验
照片墙是一个可自由摆放的照片记忆空间，默认以完整墙面全景浏览为主，不是传统网格相册。
- **浏览模式**：全景自由墙，可查看墙面；另有类似 QQ 相册的时间轴海报浏览模式。时间轴海报只读，绝不能反向修改自由墙中照片的 x/y、旋转、层级、涂鸦、贴纸。
- **编辑模式**：显式进入后才允许移动、缩放、旋转、编辑相框等；工具切换要清楚，不能由一个触摸动作同时触发多种操作。
- **摆照片模式**：拖动照片位置、调整布局；照片位置、大小、旋转、层级和布局应保存并在重进后恢复。
- **涂鸦模式**：在照片内容区域绘画，笔迹位置应与触点精准对应；不能因为点到照片就打开图片编辑，也不能把照片拖动或翻转。
- **锁定模式**：锁住照片位置，防止误触移动；模式按钮状态要清楚。
- 支持相框级贴纸/涂鸦、模板/形状排布、整墙 PNG 导出。模板应让少量和大量照片都能看出轮廓，照片既能吸附模板骨架也能自由拖拽并持久化。
- 视觉方向：奶油色、拍立得、信纸/手账、墙面氛围和精致纹理；避免深暗、绿为主、默认大圆角卡片。浏览模式要有整墙全景感，设置模板放在设置页，不要把设置控件塞满照片墙。
- 双指捏合缩放、单指平移/浏览等手势必须有明确且互不冲突的规则；移动端单指操作不能被误判为涂鸦/图片编辑。

### 4.2 用户最新报告的严重问题
用户 2026-10-21 明确反馈：
- **单指滑动已经不能用了**，用户觉得非常不方便。
- **涂鸦完全崩溃，根本画不了**。
- **照片位置一直在挪动**，布局不稳定。
- 用户认为之前的修改把照片墙弄坏了，要求停止零碎修补，查根因并整体理清交互。
这些都必须先修复，再谈装饰优化。当前状态应标记为“存在严重回归，待修复和验收”。

### 4.3 已知的近期代码修改线索（必须重新核验，不要直接信任）
最近修改过以下文件：
- `components/photo-wall-app.tsx`：调整画布容器布局；增加“合照角色参考图”选择，将用户勾选的角色参考图用于“想留住的瞬间”生成；选择存入 localStorage。
- `components/photo-wall/photo-wall-canvas.tsx`：改过涂鸦命中检测，使涂鸦模式命中照片图像而不是整张拍立得边框；修改坐标换算，使用元素 offset 尺寸与 canvasZoom 计算点位。
- `lib/photo-wall-templates.ts`：改过心形模板点位分布，先放轮廓点，再用最远点采样填充内部，避免照片集中在中心。

### 4.4 照片墙根因排查清单
1. 绘制指针事件：检查 pointerdown/move/up/cancel、pointer capture、touch-action、preventDefault、事件冒泡和模式切换；确认同一手势没有同时被画布平移、照片拖拽、涂鸦和图片点击处理器接管。
2. 手势优先级必须显式定义：例如浏览/平移模式单指平移；摆照片模式单指拖照片、空白处平移；涂鸦模式只在图像画布上画，且不改变照片位置；双指手势专门用于缩放。具体行为以现有产品模式为准，不能靠事件竞争偶然决定。
3. 检查坐标系：CSS transform、缩放、平移、设备像素比、滚动容器、边框/相框内边距和元素 bounding rect 是否混用。坐标变换必须有唯一、可测试的数学定义。
4. 检查状态闭包与渲染：拖动过程中是否使用过期的 x/y/zoom；React 重渲染是否重置了初始位置；保存/加载是否重复应用缩放或偏移；是否因模板重排在每次渲染时重新计算照片位置。
5. 检查点击与长按冲突：点击照片不应在摆照片/涂鸦模式下意外打开图片编辑；长按、双击、翻转和拖动必须有清楚的阈值与状态。
6. 检查画布尺寸变化：容器 resize、工具栏高度变化、横竖屏和全屏切换不得悄悄重算并写回照片位置。
7. 做手动回归表：单指空白平移、单指拖照片、单指涂鸦、双指捏合、点击照片、拖拽后保存重开、切换模板、导出 PNG、进入时间轴再返回自由墙。每项都要明确期望结果。

## 6. 生活系统的功能需求（跨会话背景）

### 6.1 地点与场景
- 地点列表卡片优先展示当前地点、在场角色、氛围与“前往”操作。
- 地点库与地点编辑页面分开；地点可编辑道具、布局、描述；角色可配置习惯并查看历史统计。
- 进入场景的记录只在首次进入，或暂停/暂时离开后再次返回时产生；普通返回不重复写记录。
- 场景聊天突出地点与在场角色，聊天区空间优先；生活提示词/预设沿用已有预设系统。
- “观察生活”应合并到“角色日程”，不要保留成独立导航入口。
- “生活引擎工具开关”应放在系统设置 → 聊天工具箱，不要另造一套特殊聊天 UI。
- 同一地点的用户与角色优先使用本地/附近场景消息，避免不必要的线上消息表现。
- 旁白/动作与对白要分开显示；动作说明小号、居中、斜体且无气泡/时间戳；对白独立呈现。长按对白应可编辑、删除、重新生成并替换原消息。
- 关键按钮（返回地点列表、暂停、设置、归档等）整块区域都可点击，不应只有图标响应。

### 6.2 角色日程、邀约与共同经历
- 角色日常、邀约活动、共同经历分区展示。
- 角色每周一可依据角色卡、世界书和短期记忆生成计划；用户能编辑。
- 邀约应包含时间、地点、原因和内容，并能更新相关日程。
- 地点切换会推进时间。
- 生活记录可由用户主动点击生成场景图，不应自动消耗生成额度。

## 7. 聊天与其他重要模块

- 多图合并发送应是类似微信的单条集合消息，气泡内横向轮播/滑动查看，不是多条独立图片消息；“发送后合并展示”勾选后只生成一条特殊集合消息。
- Android 离线/后台推送、回复、通话、桌面小组件等原生能力必须考虑 WebView 与浏览器差异。WebView 不一定支持浏览器 Notification API；不能声称清掉后台后仍能推送，除非 Android 原生链路已实测。
- 线上聊天、角色记忆、工坊 Agent、MCP/工具调用等已有能力需要保留；不要为美化界面改掉工具调用/数据流。
- 下载/导出等动作要提供成功或失败反馈。
- 主题色改变时文字、开关和强调色应适配；用户希望强调色能跟随主题或可自定义色号，并有多套主题预设。
- 用户关心多机型兼容性，尤其 WebView、刘海/打孔屏、安全区、横竖屏、系统返回手势。曾以荣耀 500 Pro 为参考设备，但不能把尺寸写死在代码里；华为 Mate 70 Pro+ / HarmonyOS 4.3.0 曾出现壳层部分白屏而直开网页正常的问题。
- APK 更新涉及签名；自托管/云端数据结构变化可能需要部署；README 应解释 GitHub Actions APK 构建、签名和自托管配置。用户不希望反复接受包名重命名教程。
- 云备份存储用量历史上偏高，用户解释有定时自动云备份，不要简单把文件增长认定为垃圾数据；需要区分备份对象、缓存、日志和媒体文件。

## 8. 代码质量、诊断与兼容性要求

- 不要使用 `ignoreBuildErrors: true` 掩盖类型错误；CI 应执行 TypeScript 检查（例如 `npx tsc --noEmit`）与正式构建，实际脚本以仓库当前配置为准。
- Kotlin 构建历史问题包括 namespace/R/BuildConfig 不匹配和 keystore 密码配置错误；验证 Android 构建时需看完整日志，不要仅看 workflow 名称。
- 诊断系统目标是把 WebView console、JS 异常、原生崩溃/桥接问题和设备兼容性信息汇总到一个模块，方便用户反馈；不要把故障诊断和兼容性诊断拆成多个难找页面。
- 设备特定行为应做能力检测与合理降级，不应依赖固定屏幕尺寸或某一机型特例。
- 原生桥接应校验调用来源与 URL scheme，避免任意页面调用危险能力；外链仅允许明确允许的 http/https 方案。
- 不要引入未经验证的依赖或不受控公共代理；需要新增库时评估体积、维护、WebView 兼容和部署成本。

## 9. 开发与验收工作流

每个复杂模块建议按此流程执行：

### A. 先审计现状
- 读取 main 当前文件与相关调用方、CSS、hooks、类型、数据结构、历史提交。
- 画出关键状态/事件流，明确一个事件由哪个组件负责，避免多个监听器互相抢事件。
- 将“现有行为”“用户要求”“当前故障”“潜在回归”分开记录。

### B. 形成整块改造
- 明确页面信息架构、状态模型、交互模式和移动端手势优先级。
- 对核心组件进行成组修改，不要用大量局部覆盖样式堆叠旧结构。
- 尽量避免大范围盲目重写；如果需要重构，先定义旧功能的保留清单和迁移策略。

### C. 自检
- TypeScript/lint/单元测试（仓库有何命令就实际运行何命令）。
- 生产构建。
- Android Gradle 构建（如果改了原生桥或 WebView 行为）。
- 通过 GitHub Actions 检查真实 run、job、step 和失败日志；没有 run 就明确写“未触发/未验证”。
- 检查 diff，确保未修改无关模块、未覆盖用户数据、没有意外删除功能。

### D. 功能回归与用户验收
- 网页与 APK 分别测试；有必要时让用户提供设备/链接做最终真机验证。
- 输出只说明：改了什么、测试了什么、哪些通过、哪些没法验证/仍有风险、对应 main commit。
- 不要把“提交成功”说成“问题已解决”。对播放、触控、方向切换等设备行为尤其如此。
